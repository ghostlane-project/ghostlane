# olcbox — what is missing, technically and product-wise

**Date:** 2026-08-14
**Inspected:** `ghostlane-project/ghostlane` @ `main` `f1471d7` (release 1.0.273), plus the
specs and coordinator routes in the proofkit repo.
**Status:** findings only — nothing here has been agreed or started.

Everything below was read out of the code on the date above, not recalled. Each item
carries the evidence so it can be re-checked rather than re-argued.

---

## Where the app already stands

Worth stating, because the gaps only make sense against it: KMP client on Android,
iOS, macOS, Windows and Linux; five transports (olcRTC, VLESS Reality, Hysteria2,
XHTTP, VLESS TLS) over two cores (sing-box exec'd, Xray exec'd, libbox in-process on
iOS); server lists with auto-refresh, quota from `subscription-userinfo`, expiry, and
crypt1/crypt5 encrypted links; live olcRTC room occupancy; a tunnel verifier that
proves the exit rather than trusting the steps; per-app split tunnelling and a
watchdog on Android; TUN on all three desktops; log scrubbing; ProofKit Cypherpunk
skin. Roughly 12k lines of commonMain and 31 test files.

## Technical

### 1. Transport auto-fallback is written and not wired — the biggest hole

`docs/superpowers/specs/2026-07-24-olcbox-transport-autofallback-design.md` (proofkit
repo) is marked *Design, ready to implement*. Part of it was built:

- `sharedUI/.../net/TransportGroup.kt` — grouping by `(subscriptionUrl, base name)`
- `sharedUI/.../net/TransportSelector.kt` — `orderCandidates()`, last-known-good first,
  then Reality → Hysteria2 → XHTTP
- `sharedUI/src/commonTest/.../net/TransportFallbackTest.kt` — both covered

And then never connected. Verified by grep across every `.kt` and `.swift` outside
`build/`:

- `orderCandidates()`, `siblings()`, `groupByExit()` are called **only from
  `TransportFallbackTest.kt`**
- the sole production caller of anything in these files is `TransportGroup.baseName()`,
  used for a display label in `HomeScreen.kt:291` and `MainViewController.kt:236`
- `TransportProbe.kt`, the probe half of the design, **does not exist**

What is left, per the spec: start the candidate core on an ephemeral local SOCKS port
with no tun/VpnService involvement, probe it with one HTTP request (the CI tunnel
tests already curl through exactly such a port), kill it, and only then hand the winner
to the connect path. Plus a user-visible off switch, default on.

**Why it matters:** when DPI shifts and Reality stops passing, the user is the fallback
algorithm — scrolling for a row ending in `· XHTTP` and trying again. That is the work
the product exists to remove.

### 2. No kill switch, no always-on, anywhere

Grepped for `alwaysOn`, `isAlwaysOn`, `killSwitch`, `onDemand`, `allowBypass` — no hits
in any source file.

- **Android:** no always-on / lockdown handling
- **iOS:** no `NEOnDemandRule`, which would also give auto-connect for free
- **Desktop:** nothing fail-closed when a core dies with routing still in place

For users in RU/IR a leak during a reconnect is the failure that costs most, and it is
the one moment the app currently says nothing about.

### 3. iOS survivability lags Android — narrowly, but in the places that bite

Android (`sharedUI/src/androidMain/.../vpn/service/OlcboxVpnService.kt`, 1949 lines):
stall watchdog reading tun byte counters (catches "connected but nothing moves" —
exactly the failure `TunnelVerifier`'s comment describes), `ConnectivityManager.NetworkCallback`,
exponential reconnect backoff.

iOS (`iosApp/PacketTunnel/PacketTunnelProvider.swift`): `NWPathMonitor` **does** exist and
on an interface change calls `server.resetNetwork()` (`:247-255`). But that is libbox
only — `OlcrtcEngine` and `XrayEngine` are separate and get nothing — and there is no
stall watchdog at all. Wi-Fi↔cellular and sleep/wake are the commonest real-world breaks.

Parity here is worth more than any new feature.

### 4. Zero field observability

`LogScrubber` and log export exist; everything stays on the device. For a
censorship-circumvention product the operationally decisive fact is *which transport
died in which country today*, and there is currently no way to learn it.

Not Firebase. Two narrower things: opt-in aggregate telemetry of
`country + transport + connect success/failure` carrying no destinations and no IP; and
a user-initiated diagnostic report posted to the coordinator under a one-time code.
This data exists nowhere else and feeds directly into which transports to keep running
on the nodes.

### 5. iOS never compiles in CI

`.github/workflows/pr-checks.yml` skips iOS deliberately — macOS runner minutes bill at
10x. Consequence: the first compile of any shared-code change on iOS is a manual Xcode
build. A single `compileKotlinIosArm64` job on PRs is cheap and catches nearly all of it.

## Product

### 1. The funnel ends on an empty screen

A fresh install shows `"Import a server list to start"` (`RelayStatus.kt:63`) and offers
nothing else. Every user must already possess a link from somewhere.

The backend for fixing this exists — `bot-register` and the partner mint in
`coordinator/src/routes/partner_api.rs`. On Android and desktop, where Apple's 3.1.1
constraint does not apply, a "try it" path could mint a trial token and have someone
connected in about thirty seconds. iOS stays as it is.

### 2. olcRTC is the whole 4.3 answer and reads as one row in a list

The listing has already been rewritten around "a tunnel inside a video call"
(`docs/app-store-listing.md`), and live room occupancy works
(`net/OlcrtcStatus.kt` → `GET /api/v1/olcrtc/status`). In the UI it is still one
location among many. If it is the differentiator, it should be a first-class thing in
the app, with an in-app account of why it passes where nothing else does.

### 3. No localisation at all

`stringResource` appears in **zero** files; every user-visible string is hardcoded
English across 63 commonMain files. The audience is RU/IR/CN. Both store listings
justify English-only on the grounds that *the app* has no translations — so the
causality starts here. Largest single lever on conversion in the target market, and
the most tedious refactor on this page.

### 4. Distribution is asymmetric and manual

`release.yml` is `workflow_dispatch` only — a push to main ships nothing. macOS is
signed and notarised, Windows signs when the secrets are present. While iOS sits in
review, Android and desktop are the entire channel, and the Play listing exists as copy
(`docs/play-listing.md`) with no sign in the repo that it was submitted.

---

## Suggested order

1. Finish transport auto-fallback — spec written, half the code exists, needs the probe
   and the wiring
2. Kill switch + iOS on-demand
3. iOS survivability parity (engine-aware network reset, stall watchdog)
4. Transport telemetry
5. Trial funnel on Android/desktop

The first three are about what the app is obliged to do by itself; the rest is growth.
