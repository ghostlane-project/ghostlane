### macOS: the tunnel's own listener stays off the PAC server's old port

In an olcRTC session the tunnel's verification listener took the port after the room's SOCKS port, 10809, which was this app's PAC server's port until July. What still asks that port for a PAC, with HTTP — a PAC URL an older build left enabled in the system's proxy settings, other local software by convention — knocked at a SOCKS listener, and every knock was an "invalid argument" line in the tunnel's log, four to six every ten seconds, crowding out what the log is read for. The listener now keeps clear of that port; the knocks meet a closed port and leave no trace. The leftover PAC URL itself is the next step ([#139](https://github.com/ghostlane-project/ghostlane/issues/139)).

### Server lists: the app names its device to the list's provider

A provider can limit how many devices receive one subscription, the way Happ and v2RayTun already speak it: with every refresh of a server list the app now sends a random id made at install (`x-hwid`), the device's system and its version and the device model, and nothing else about the device or its owner, so the provider can count the devices on a subscription. The iOS packet tunnel's room refresh and the Linux CLI send the same, and the tunnel's id is the app's. A list whose provider turns the device away is kept with the reason in place of its servers and is not asked again without the id: until now such an answer was retried as an unknown app, which the provider either refused again or served without counting, and the one placeholder line it carries was shown as a server. On iOS the privacy manifest declares the id.
